# LibreBread v2 Technical Design

Date: 2026-05-19

Status: proposed design for implementation planning

## Context

LibreBread v1 in `/home/ioa/projs/librebread_v1` is a multi-protocol mock service for testing integrations:

- SMS: LibreSMS, DevinoTelecom, SmsRU.
- Mail: SMTP receiver, POP3 mock, email index page.
- Flashcall: LibreCall mock.
- Online payments: native LibrePayment and TinkoffPayment mock.
- Push: LibrePush mock.
- Telegram: Telegram Bot API mock.
- Realtime: SSE broker for email, helpdesk and SMS browser notifications.

The current repository is already a v2 rewrite. It has:

- Go module `github.com/vasyahuyasa/librebread`.
- `net/http` server wrapper in `web`.
- OpenAPI-first HTTP API in `api/openapi_librebread.yml`.
- Generated `chi` router and models via `oapi-codegen`.
- SQLite migrations and one SQL-backed SMS repository.
- A small server-rendered HTML UI for SMS.

The design below treats v1 as the behavioral reference, but does not preserve v1's package layout. v2 should be contract-first, persistent by default, testable at repository and handler boundaries, and small enough to remain a reference application.

## Design Goal

Build LibreBread v2 as a single binary that receives mock external-provider calls, stores every received artifact in SQLite, exposes list/detail UI pages and JSON APIs, and publishes realtime browser notifications for new mock events.

The service should remain useful locally without external dependencies. Redis, Postgres, frontend build tools, and message brokers are not required for this roadmap.

## Non-Goals

- Full compatibility with every edge case of real DevinoTelecom, SmsRU, Tinkoff, Telegram, SMTP, or POP3.
- Real email delivery, SMS delivery, Telegram delivery, card processing, or mobile push delivery.
- Multi-node deployment. SQLite plus in-process notifications intentionally targets one process.
- Replacing OpenAPI with RPC or GraphQL.
- Building a heavy SPA.

## Architectural Decision Summary

Recommended approach: keep the current v2 direction and make it strict.

- HTTP contract: OpenAPI 3.0.3 as the source of truth for every HTTP endpoint.
- Router: generated by `oapi-codegen` using `chi`.
- Storage engine: SQLite with WAL, migrations, explicit repositories, and transactions.
- Realtime technology: Server-Sent Events.
- UI: server-rendered HTML plus small progressive JavaScript for live updates and browser notifications.
- Mail protocols: document SMTP and POP3 in a protocol appendix because OpenAPI only describes HTTP. Link that appendix from the OpenAPI `externalDocs`.

## Alternatives Considered

### Option A: Contract-first monolith with SQLite and SSE

This is the recommended option. It matches the current repository and gives a clean path from v1. SQLite is already present, migrations are already embedded, and `oapi-codegen` is already configured. SSE is sufficient because notifications are server-to-browser only.

Trade-off: this is not a distributed architecture. That is acceptable because LibreBread is a local mock/test service.

### Option B: Split service with Postgres, Redis, WebSocket and SPA

This would make scaling and bidirectional communication easier, but it adds operational dependencies that are not needed for a mock integration server. It also moves the project away from a lightweight reference application.

Trade-off: more extensible at the cost of more moving parts and weaker local ergonomics.

### Option C: File/event-log storage with replay

This is close to v1 and easy to inspect manually. It is weaker for querying payments, notification attempts, Telegram payloads, and list pages. It also makes migrations and invariants harder to maintain.

Trade-off: simple writes, poor schema evolution.

## Package Structure

Use domain packages and keep generated API code separate from domain logic.

Proposed structure:

```text
api/
  openapi_librebread.yml
  librebread.gen.go
  handler.go
  errors.go
  render/
application/
  application.go
internal/
  domain/
    sms/
    mail/
    flashcall/
    push/
    payment/
    telegram/
    notification/
  storage/sqlite/
    db.go
    sms.go
    mail.go
    flashcall.go
    push.go
    payment.go
    telegram.go
    outbox.go
  webui/
    templates.go
    assets.go
migrations/
web/
  server.go
cmd/librebread/
  main.go
docs/
  protocols/mail.md
  superpowers/specs/
```

Rationale:

- `api` owns generated HTTP glue and OpenAPI-facing DTO mapping.
- `internal/domain/*` owns validation, state machines, and service interfaces.
- `internal/storage/sqlite/*` owns SQL, migrations, transactions, and persistence mapping.
- `internal/domain/notification` owns in-process publication and replay from durable storage.
- `internal/webui` owns templates and static assets so generated API code does not grow UI responsibilities.

## OpenAPI Design

### General Rules

All HTTP endpoints must be present in `api/openapi_librebread.yml`. Generated router code is the only route registration surface for HTTP endpoints covered by OpenAPI.

Each endpoint should define:

- `operationId`.
- request body schema or parameter schema.
- JSON responses.
- HTML responses for UI pages where applicable.
- stable error schema for JSON APIs.
- compatibility notes for v1 aliases.

Use content negotiation as the primary selector:

- `Accept: text/html` returns UI.
- `Accept: application/json` returns JSON.

Keep v1-compatible query flags as secondary aliases:

- `?format=json`
- `?format=html`
- `?json=1`

### Error Model

JSON APIs should use one shared schema:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "phone must contain 10 or 11 digits",
    "details": {
      "field": "phone"
    }
  }
}
```

HTML APIs may use plain HTML error pages, but handlers should classify domain errors before writing responses:

- `400` for malformed or invalid input.
- `404` for missing stored records.
- `405` for unsupported HTTP method.
- `409` for state conflicts when a state transition is impossible.
- `422` for syntactically valid requests that violate domain rules.
- `500` only for unexpected infrastructure failures.
- `501` only for intentionally unimplemented compatibility endpoints such as `/libre/check`.

## SMTP and POP3 Documentation

OpenAPI must not pretend to describe SMTP or POP3. It describes HTTP only.

Add `docs/protocols/mail.md` and link it from OpenAPI `externalDocs`. The mail protocol document should specify:

- SMTP listen address and default port: `:25`.
- POP3 listen address and default port: `:110`.
- TLS behavior: disabled by default for SMTP/POP3 in v2 unless explicit configuration is added.
- Authentication behavior: anonymous SMTP accepted; POP3 uses dummy auth until a mailbox model exists.
- Accepted SMTP commands through `github.com/emersion/go-smtp`.
- Maximum message size and recipient count.
- Stored fields extracted from MIME headers: `Message-Id`, `Date`, `From`, `To`, `Subject`, body.
- How SMTP inserts into the same `mail_messages` table used by `/libre/mail/send`.
- POP3 v2 scope: mock server only. It may expose static/dummy mailbox behavior until a real POP3 storage adapter is designed.

This keeps the HTTP contract machine-readable and the mail protocols honest.

## Storage Design

### Engine Choice

Use SQLite as the low-level storage engine.

Reasons:

- It is already integrated in v2.
- It keeps LibreBread a single local binary.
- It supports transactions, indexes, constraints, and migrations.
- It is better than append-only files for listing, filtering, payment state machines, and notification retry journals.
- It is simpler than Postgres for the intended local mock-service use case.

Use WAL mode and foreign keys on startup:

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

### Repository Style

Do not create a generic repository abstraction. Each domain gets a small explicit storage interface:

- `sms.Store`
- `mail.Store`
- `flashcall.Store`
- `push.Store`
- `payment.Store`
- `telegram.Store`
- `notification.Outbox`

Each interface should express domain operations, not SQL details. Example operations:

- `CreateSMS(ctx, message) (id, error)`
- `ListSMS(ctx, limit, offset) ([]Message, error)`
- `CreatePayment(ctx, payment) error`
- `WithPayment(ctx, id, fn) error`
- `AppendEvent(ctx, event) error`

Storage implementation lives under `internal/storage/sqlite`.

### Core Tables

Use domain tables plus a notification outbox.

`sms_messages`:

- `id TEXT PRIMARY KEY`
- `created_at DATETIME NOT NULL`
- `provider TEXT NOT NULL`
- `from_addr TEXT NOT NULL`
- `to_addr TEXT NOT NULL`
- `text TEXT NOT NULL`
- provider-specific payload as `request_json TEXT NOT NULL DEFAULT '{}'`

`mail_messages`:

- `id TEXT PRIMARY KEY`
- `received_at DATETIME NOT NULL`
- `sent_at DATETIME`
- `message_id TEXT NOT NULL`
- `from_addr TEXT NOT NULL`
- `to_addr TEXT NOT NULL`
- `subject TEXT NOT NULL`
- `body TEXT NOT NULL`
- `raw_message BLOB`
- `source TEXT NOT NULL` with values `smtp` or `libremail`

`flashcall_calls`:

- `id TEXT PRIMARY KEY`
- `created_at DATETIME NOT NULL`
- `to_phone TEXT NOT NULL`
- `from_phone TEXT NOT NULL`
- `code TEXT NOT NULL`

`push_messages`:

- `id TEXT PRIMARY KEY`
- `created_at DATETIME NOT NULL`
- `push_service TEXT NOT NULL`
- `raw_message BLOB NOT NULL`
- `validate_only BOOLEAN NOT NULL`

`push_tokens`:

- `push_id TEXT NOT NULL REFERENCES push_messages(id) ON DELETE CASCADE`
- `token TEXT NOT NULL`
- composite primary key `(push_id, token)`

`telegram_requests`:

- `id TEXT PRIMARY KEY`
- `created_at DATETIME NOT NULL`
- `bot_token TEXT NOT NULL`

`payments`:

- `success_url TEXT`
- `fail_url TEXT`

`payment_notification_attempts`:

- `delivered_to_sse BOOLEAN NOT NULL DEFAULT 0`

### Transaction Rule

Any handler that creates or changes a domain object and emits a realtime notification must write both the domain row and `notification_events` in the same SQL transaction.

This provides the invariant:

```text
If a domain mutation is committed, the corresponding notification event is committed.
```

The in-process SSE broker may miss an event during a crash, but the durable event remains available for replay or future catch-up behavior.

## Domain State Machines

### SMS

SMS records are immutable after insert. Provider-specific handlers map incoming request fields to the common SMS model and save the original request payload for inspection.

### Flashcall

Validation rules inherited from v1:

- `code` length is 1 to 4 characters.
- `code` contains only digits.
- `phone` length is 10 or 11 characters, with optional leading `+`.
- generated caller number ends with the requested code.

Flashcall records are immutable after insert.

### Push

`validate_only=true` returns a successful dry-run response and does not persist a push message. `validate_only=false` persists the request, stores tokens, and emits `push.created`.

### LibrePayment

Native payment statuses:

- `new`
- `confirmed`
- `rejected`

Allowed transitions:

- `new -> confirmed`
- `new -> rejected`

Terminal states:

- `confirmed`
- `rejected`

Attempts to confirm or reject a terminal payment return `409` or `422`; choose `409` for UI actions and `422` for provider-compatible API behavior where v1 already used it.

### TinkoffPayment

Tinkoff mock processes should be stored in the shared `payments` table with `provider='tinkoff'`, plus provider-specific data in `payload_json`. Keep response shapes compatible with v1 for:

- `Init`
- `Charge`
- `GetState`

Do not mix Tinkoff token generation or notification signing with native LibrePayment logic. Keep them as payment-domain adapters.

### Telegram

Every Telegram bot method request is stored with token, method, normalized payload, and response payload. `sendMessage` returns a realistic Telegram-shaped JSON response as v1 does. Unknown methods return `{}` inside `{"ok": true, "result": {}}`.

## Realtime Notifications

### Technology Decision

Use Server-Sent Events for v2.

Reasons:

- All roadmap notifications are server-to-client.
- Browser `EventSource` is built in and works without a frontend framework.
- SSE is simpler to test than WebSocket.
- Long polling is less efficient and more complex at the handler layer.
- WebRTC is the wrong abstraction for service notifications.

### Event Stream

Endpoint:

```text
GET /events
```

Response:

```text
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```

Each event uses named SSE events:

```text
event: sms.created
id: 01HX...
data: {"id":"...","provider":"smsru","to":"+7999...","text":"...","created_at":"..."}
```

Initial event kinds:

- `sms.created`
- `mail.created`
- `flashcall.created`
- `push.created`
- `telegram.created`
- `payment.created`
- `payment.updated`

The roadmap explicitly requires notifications for mock SMS, mock flashcall, and mock PUSH. Those three must be implemented in the first realtime slice.

### Browser and Phone Behavior

Browser and mobile browser support should be implemented through:

- `/events` SSE subscription while the LibreBread page is open.
- Browser Notification API after the user grants permission.
- In-page updates for users who do not grant notification permission.

Native phone push is outside this roadmap. A mobile browser can receive notifications while the page remains open; OS-level background push would require Web Push subscriptions and a separate design.

## UI/UX Design

Use server-rendered HTML with progressive enhancement.

Principles:

- No frontend build system for this roadmap.
- One global layout with navigation for SMS, Email, Push, Flashcall, Payments, Telegram.
- Dense, readable operational views instead of marketing pages.
- Tables for high-cardinality lists, detail pages for large payloads.
- Each list has count, latest-first ordering, limit selector, and JSON link.
- Realtime events update visible list counts and prepend new rows when the user is on the matching page.
- Browser notification permission is requested by explicit user action, not on load.

Suggested UI assets:

- Embedded CSS in `internal/webui/assets.go` or static files served from embedded FS.
- A small `events.js` that opens `EventSource`, dispatches by event type, and updates the current page.

Do not put UI rendering in generated API code. Handlers should call a `webui.Render*` function after domain data has been loaded.

## Application Startup

Startup sequence:

1. Load configuration from environment and defaults.
2. Open SQLite.
3. Enable WAL, foreign keys, and busy timeout.
4. Run migrations.
5. Construct SQLite repositories.
6. Construct domain services.
7. Construct notification broker and connect it to the notification outbox.
8. Construct OpenAPI handler implementation.
9. Start HTTP server.
10. Start SMTP server when enabled.
11. Start POP3 server when enabled.
12. Wait for signal and shut down servers with context deadlines.

Configuration:

| Variable | Default | Purpose |
|---|---|---|
| `LIBREBREAD_HTTP_ADDR` | `:80` | HTTP listen address. |
| `LIBREBREAD_DATABASE_PATH` | `data.db` | SQLite database path. |
| `LIBREBREAD_SMTP_ADDR` | `:25` | SMTP listen address. |
| `LIBREBREAD_POP3_ADDR` | `:110` | POP3 listen address. |
| `LIBREBREAD_ENABLE_SMTP` | `true` | Start SMTP server. |
| `LIBREBREAD_ENABLE_POP3` | `true` | Start POP3 server. |
| `LIBREPAYMENT_BASE_URL` | `http://localhost` | Base URL for generated native payment links. |
| `USER` | empty | Optional basic auth login, v1-compatible. |
| `PASSWORD` | empty | Optional basic auth password, v1-compatible. |

## Migration Strategy from v1

This is a rewrite, not an in-place data migration. The v1 files are behavioral references.

Port order:

1. OpenAPI cleanup and route generation.
2. SQLite storage foundation and migrations.
3. SMS providers and list UI.
4. SSE notification foundation for SMS.
5. Flashcall storage, API, list UI, notification.
6. Push storage, API, list/detail UI, notification.
7. Mail storage, LibreMail HTTP API, SMTP receiver, email list UI.
8. Telegram mock API and list UI.
9. LibrePayment and TinkoffPayment APIs, payment UI, notification journal.
10. UI polish and cross-page realtime updates.

This order keeps every milestone runnable and testable.

## Verification Strategy

### Contract Verification

- Run OpenAPI validation in CI.
- Run `go generate ./api` and fail CI if generated code changes are not committed.
- Add handler tests for every operationId.
- Add compatibility tests for v1 endpoint aliases.

### Storage Verification

- Use SQLite in temporary files for repository tests.
- Verify migrations from empty database.
- Verify indexes for list queries with `ORDER BY created_at DESC LIMIT ?`.
- Use transaction tests for each mutation that emits notifications.

### Domain Verification

Property-style tests should cover:

- Flashcall generated caller number always ends with the requested code.
- Flashcall rejects invalid code and phone formats.
- Payment terminal states cannot transition again.
- Push dry-run never creates stored messages or notification events.
- Every persisted SMS, flashcall, and push mutation creates exactly one notification event.

### Realtime Verification

- Handler test connects to `/events`, creates an SMS, and verifies an `sms.created` event arrives.
- Same for `flashcall.created` and `push.created`.
- Test client disconnect removal to avoid leaked subscribers.

### UI Verification

- Golden tests for core HTML fragments.
- Escaping tests for user-controlled text in SMS, email, push, Telegram payloads.
- Manual browser check for list pages and notification permission flow.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| OpenAPI spec becomes invalid while adding many endpoints. | Add validation and generated-code diff checks early. |
| Generated API types leak into domain packages. | Keep mapping in `api` and keep domain packages independent. |
| SQLite write contention during tests or bursts. | WAL, busy timeout, short transactions, one process assumption. |
| SSE clients block the broker. | Use bounded per-client channels and drop or disconnect slow clients. |
| v1 route inconsistencies break existing users. | Keep aliases for known inconsistencies such as SmsRU `/sms/send` and `/sms/user/send`. |
| SMTP/POP3 scope expands beyond mock behavior. | Keep protocol document explicit: SMTP stores messages, POP3 remains mock until separately designed. |
| UI becomes a large SPA. | Keep server-rendered pages and small JS modules only. |

## Acceptance Criteria

The roadmap is complete when:

- `api/openapi_librebread.yml` describes every HTTP method listed in this design.
- The HTTP router is generated from the OpenAPI spec.
- All current v1-referenced HTTP providers have handlers in v2.
- SMS, mail, flashcall, push, payments, and Telegram data persist in SQLite.
- SMS, flashcall, and push create realtime SSE notifications.
- Browser pages update or notify without reload when relevant events arrive.
- SMTP stores mail into the same mail storage as LibreMail API.
- POP3 behavior is documented and enabled as a mock server.
- UI pages are modern, lightweight, and usable on desktop and mobile browser widths.
- Tests cover OpenAPI generation, storage repositories, domain validation, provider compatibility, and realtime notifications.
